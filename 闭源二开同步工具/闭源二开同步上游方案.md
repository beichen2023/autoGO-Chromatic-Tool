# 闭源二开并同步上游方案

本文档说明如何把一个开源仓库独立迁移成内部私有仓库，同时保留本地同步原作者后续更新的能力。这个方案适合内部测试、商业验证、临时闭源二开等场景。

## 核心思路

不要使用 GitHub 的 Fork 按钮创建公开关联仓库，而是把原仓库镜像到一个新的私有仓库中。

这样做以后，GitHub 不会把你的仓库识别成原仓库的 fork，因此页面上也不会有 `Sync fork` 按钮。同步上游更新改成本地通过 `upstream` 远程仓库完成。

最终远程关系应当是：

```text
origin   -> 你自己的私有仓库，负责保存内部二开代码
upstream -> 原作者的公开仓库，只负责拉取上游更新
```

## 一次性闭源迁移流程

### 1. 在 GitHub 创建私有仓库

先在你的 GitHub 账号或组织下创建一个新的私有仓库，例如：

```text
https://github.com/your-username/autoGO-Chromatic-Tool.git
```

注意不要点击原仓库页面的 Fork 按钮。直接新建一个空仓库，并设置为 `Private`。

### 2. 镜像克隆原作者仓库

在本地执行：

```bash
git clone --mirror https://github.com/xiaozhang959/autoGO-Chromatic-Tool.git autoGO-Chromatic-Tool.git
cd autoGO-Chromatic-Tool.git
```

`--mirror` 会完整复制分支、标签、引用等历史信息，适合做一次性迁移。

### 3. 推送到自己的私有仓库

```bash
git remote set-url origin https://github.com/your-username/autoGO-Chromatic-Tool.git
git push --mirror
```

推送完成后，你的私有仓库已经拥有原仓库的完整历史，但它在 GitHub 上是一个独立项目。

### 4. 删除临时镜像目录

镜像仓库是裸仓库，不适合日常开发。推送完成后可以删除本地的 `autoGO-Chromatic-Tool.git` 目录。

### 5. 正常克隆私有仓库用于开发

```bash
git clone https://github.com/your-username/autoGO-Chromatic-Tool.git
cd autoGO-Chromatic-Tool
```

从这一步开始，你的日常开发都在私有仓库里进行。

## 绑定上游仓库

在私有仓库的本地工作区中添加原作者仓库作为 `upstream`：

```bash
git remote add upstream https://github.com/xiaozhang959/autoGO-Chromatic-Tool.git
git remote -v
```

检查结果应类似：

```text
origin   https://github.com/your-username/autoGO-Chromatic-Tool.git (fetch)
origin   https://github.com/your-username/autoGO-Chromatic-Tool.git (push)
upstream https://github.com/xiaozhang959/autoGO-Chromatic-Tool.git (fetch)
upstream https://github.com/xiaozhang959/autoGO-Chromatic-Tool.git (push)
```

建议把 `upstream` 的 push 地址禁用，避免误推到原作者仓库：

```bash
git remote set-url --push upstream DISABLED
```

之后再执行 `git remote -v`，你会看到 `upstream` 的 push 地址变成 `DISABLED`。这样本地仍然可以拉取上游更新，但不会误推。

## 日常二开分支建议

推荐不要直接在原始 `master` 或 `main` 上做大量内部修改，而是建立一个内部开发分支，例如：

```bash
git checkout -b master-mzh-20260606
git push -u origin master-mzh-20260606
```

这样做的好处：

1. 上游主分支保持清晰，方便对比。
2. 内部改动集中在自己的分支，冲突范围更明确。
3. 后续同步上游时，可以把 `upstream/master` 合并到内部分支。

当前项目使用的分支名是：

```text
master-mzh-20260606
```

## 日常同步上游更新

假设原作者主分支是 `master`，你的内部二开分支是 `master-mzh-20260606`：

```bash
git fetch upstream --prune
git checkout master-mzh-20260606
git merge --no-ff upstream/master
git push origin master-mzh-20260606
```

如果原作者主分支是 `main`，则把 `upstream/master` 改为 `upstream/main`。

### 合并冲突处理

如果出现冲突，Git 会暂停合并。处理方式：

```bash
git status
```

逐个打开冲突文件，保留需要的代码后执行：

```bash
git add 冲突文件
git commit
git push origin 当前分支
```

如果确认这次同步不想继续，可以中止合并：

```bash
git merge --abort
```

### 为什么默认建议 merge

同步上游有两种常见方式：`merge` 和 `rebase`。

本项目建议默认使用 `merge`，因为内部二开仓库通常多人协作，`merge` 不会改写已经推送过的提交历史，风险更低。

`rebase` 的历史更线性，但会改写本地提交。如果分支已经被别人拉取，后续容易产生历史分叉。除非团队明确约定，否则不建议作为默认同步方式。

## 安全注意事项

1. 私有仓库要确认 GitHub 页面显示为 `Private`。
2. 不要把内部密钥、账号、接口地址直接提交到仓库。
3. 建议添加 `.env`、本地配置文件、构建产物到 `.gitignore`。
4. `upstream` 只用于拉取，不建议保留真实 push 地址。
5. 同步上游前先确认工作区干净，避免把未完成代码混进合并提交。
6. 上游协议、许可证仍需遵守。闭源内部测试不等于可以忽略原项目许可证限制。

## 推荐命令速查

查看远程仓库：

```bash
git remote -v
```

查看当前分支：

```bash
git branch --show-current
```

查看工作区状态：

```bash
git status --short
```

拉取上游信息：

```bash
git fetch upstream --prune
```

合并上游主分支：

```bash
git merge --no-ff upstream/master
```

推送内部分支：

```bash
git push origin 当前分支名
```

## 使用配套脚本

项目里提供了一个可迁移工具目录：

```text
闭源二开同步工具/
  当前仓库转闭源.bat       -> 调用 GitHub API，把 origin 指向的仓库改成 Private
  闭源同步上游.bat         -> 配置 upstream，并把上游更新同步到内部二开分支
  闭源二开同步上游方案.md  -> 本说明文档
```

以后迁移到别的项目时，把整个 `闭源二开同步工具` 文件夹复制到目标项目根目录即可。脚本启动时会自动把“工具目录的上一级”当作 Git 仓库根目录，所以可以从项目根目录运行，也可以进入工具目录后运行。

如果直接双击 `当前仓库转闭源.bat`，脚本会进入交互菜单，不传参数也不会一闪而过。

这两个脚本职责不同。`闭源同步上游.bat` 不会改变 GitHub 仓库可见性；仓库是否闭源由 GitHub 远端设置决定，需要使用 `当前仓库转闭源.bat` 或在 GitHub 页面手动修改。

### 把当前 origin 仓库改成私有

先查看当前仓库可见性：

```bat
闭源二开同步工具\当前仓库转闭源.bat status
```

把仓库改成私有：

```bat
闭源二开同步工具\当前仓库转闭源.bat private ghp_xxx
```

也可以通过环境变量传入 Token，避免把 Token 留在命令历史里：

```bat
set GITHUB_TOKEN=ghp_xxx
闭源二开同步工具\当前仓库转闭源.bat private
```

Token 权限建议：

```text
Classic token：repo 权限
Fine-grained token：目标仓库 Administration 读写权限
```

脚本只会修改 `origin` 指向的 GitHub 仓库，不会修改 `upstream` 原作者仓库。执行成功后，脚本还会把 `upstream` 的 push 地址设置为 `DISABLED`，避免误推到原作者仓库。

### 同步上游更新

首次绑定上游：

```bat
闭源二开同步工具\闭源同步上游.bat setup https://github.com/xiaozhang959/autoGO-Chromatic-Tool.git
```

同步上游 `master` 到当前分支，并推送到 `origin`：

```bat
闭源二开同步工具\闭源同步上游.bat sync master
```

同步上游 `master` 到指定内部分支：

```bat
闭源二开同步工具\闭源同步上游.bat sync master master-mzh-20260606
```

使用 `rebase` 模式同步：

```bat
闭源二开同步工具\闭源同步上游.bat sync master master-mzh-20260606 rebase
```

查看帮助：

```bat
闭源二开同步工具\闭源同步上游.bat help
```

脚本会在同步前检查：

1. 当前目录是否是 Git 仓库。
2. 工作区是否干净。
3. 是否存在 `origin`。
4. 是否存在 `upstream`。
5. 指定的上游分支是否存在。

如果合并或变基出现冲突，脚本会停止并提示你手动处理，避免自动覆盖内部二开代码。
